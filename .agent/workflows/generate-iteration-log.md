---
description: 自动基于更新和对话上下文总结并生成 Agent 迭代日志
---
当用户请求执行“写入迭代日志”、“总结迭代记录”或执行本工作流时，请严格按照以下标准化步骤，梳理本次更新的内容，并将改动归档。

1. **收集更新上下文与变更信息**
   - **读取活动版本资产**：AI 优先读取 `_docs/_history/v[当前]/` 下的 `plan.md`, `task.md` 与 `audit_report.md`。
   - 比较 `git status` 获取代码层真实变化。
   - 结合对话上下文，理解用户提出过的修改诉求。

2. **按标准格式起草核心摘要**
   - 从【技术架构层面】、【功能实现层面】、【底层逻辑层面】等多维度进行抽象和归纳。
   - 起草并向用户展示以下格式的日志内容：
     
     ```markdown
     ## [版本号或当天的日期，例如 v1.1.0 (2026-03-24)]
     > 核心一句话摘要（总结本次最大亮点或解决的最痛点问题）

     ### 💡 核心变动 (Core Updates)
     - **功能实现层面**：我们新增/优化了哪些具体的应用层能力？解决了哪些明显的 Bug？
     - **底层逻辑层面**：你的 Prompt、思维链或者执行决策路径发生了怎样的改变？是否调整了上下文处理机制？
     - **技术架构层面**：是否挂载了新的工具 (Tool)、加入了新的外部 API/MCP 支持、或调整了主要架构文件？

     ### 📝 规划与已知问题 (Next Steps)
     - 本次更新遗留了哪些待办？
     - 下次迭代准备突破的重点是什么？
     ```

3. **请求用户审核日志草案**
   - 生成日志草案后，务必先在聊天框中将其展示给用户浏览。
   - 询问用户：“这是此次迭代日志的草案描述，是否需要我将其写入到 `ITERATIONS.md` 中，或者您有补充的信息想要修改？”

4. **双重持久化落地 (Dual Archival)**
   - **第一步：快照备份**：保存一份完整的 Markdown 内容至 `_docs/_history/v[当前]/iteration_log.md`。
   - **第二步：总账同步**：将日志内容追加写入（Append）至根目录的 `ITERATIONS.md` 顶部。如果文件不存在则创建一个。
   - 完成后，通知用户：“发版成功！详细快照已存入 _history，变更已同步至根目录总账。”
